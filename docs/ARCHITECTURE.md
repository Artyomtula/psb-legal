# ПСБ · Юридический ассистент — как устроено решение

ИИ-ассистент для юристов банка. Отвечает на вопросы по базе нормативных актов и внутренних документов организации, ссылается на конкретные положения, учитывает редакции документов на дату события и обоснованно отказывается, если данных в базе нет.

## Как это работает

Принцип: **сначала доказательства, потом ответ, потом проверка**. Модель не отвечает «по памяти». Она оформляет положения, найденные и отобранные кодом, а каждую ссылку в ответе проставляет и проверяет код.

```
ОФЛАЙН (индекс строится при старте, кэшируется по хэшу архива базы)
  kb.zip ─► структурный парсер ─► документ → глава/раздел → статья → часть/пункт → подпункт
                                ─► пометки Гаранта («изменена с …») сохраняются как история редакций
                                ─► связи: доп. соглашение изменяет пункт договора, письмо дополняет регламент,
                                   новая редакция регламента заменяет старую (периоды действия)
                                ─► фрагменты с контекстным заголовком → BM25 по леммам (pymorphy3) + bge-m3

ОНЛАЙН (на каждый вопрос)
  1. Разбор (LLM → JSON): переформулировка с учётом диалога без добавления условий и подвопросов,
     которых пользователь не задавал; все упоминания документов, контрагентов, статей, дат и сумм.
     Каждая цитата проверяется кодом на дословное наличие в запросе; регулярки — страховочная сетка.
     Неоднозначность между договорами принимается, только если упоминание подходит к названиям
     нескольких из них; точно названный контрагент или номер договора её снимает
  2. Поиск (стартует по исходному вопросу, в диалоге — по всем репликам пользователя, параллельно
     с разбором): точные ссылки по реестру + BM25 + векторы → RRF → реранкер; после разбора добавляются
     его запросы, реранкер досчитывает только новых кандидатов
  3. Расширение: изменяющие доп. соглашения, письма-дополнения, другие редакции того же пункта
  4. Оценка доказательств (LLM): релевантность каждого фрагмента 0–3
  5. Отбор контекста (код): по дате события — применимая редакция и парная ей действующая; без даты —
     только действующая редакция; доп. соглашение — только вместе с пунктом, который оно меняет;
     при неоднозначном контрагенте — положения каждого из договоров
  6. Генерация (LLM → JSON): три варианта ответа параллельно; у каждого статус (ответ / частичный /
     нет данных / ошибка в вопросе / уточнение / отказ в противоправном / вне темы) и текст с маркерами [S#].
     Как только вариант готов, его параллельно сверяет LLM-проверяющий и для него готовится дополнение (шаг 9)
  7. Согласование (код): большинство по статусу и по выводу «да / нет», затем типичный по длине вариант
     (медиана) — случайные ошибки рассуждения, лишние сведения и пропуски отсеиваются голосованием.
     Решение принимается, как только среди готовых вариантов есть большинство (обычно два из трёх):
     третий вариант не ждём, а проверки ждём только у варианта, который будет выбран
  8. Выбор: первый согласованный вариант без замечаний проверяющего и без формальных замечаний кода,
     текст не переписывается. Если формальные замечания (маркеры, числа, цитаты, ссылки на нормы,
     прямое «да / нет», упоминание другой редакции) есть у всех вариантов — одно исправление
  9. Дополнение по пункту (LLM, ≈1 с): короткий вызов получает вопрос, ответ и полный текст только тех
     пунктов, на которые ответ ссылается, и может вернуть одно предложение из этих же пунктов — срок
     другого участника той же процедуры, другой предел того же правила, момент начала срока, что
     оплачивается отдельно. Ответ не переписывается; дополнение без маркера, с маркером чужого фрагмента,
     повторяющее ответ или добавляющее формальные замечания отбрасывается. Дополнение считается
     заранее, параллельно с проверкой варианта, поэтому время ответа не увеличивает
 10. Рендер: [S#] → «(п. 3.1 договора № … с ООО «…»)», «(ТК РФ, ст. 70, ч. 5)»; документ называется
     полностью при первой ссылке, далее — только пункт; в интерфейсе — гиперссылки на пункт документа;
     сноски об изменениях закона: в интерфейсе — свежие и будущие, в сабмите — только если событие
     произошло до изменения
```

### Поиск: разбиение, иерархия, скорость

**Разбиение.** Парсер восстанавливает структуру документа: договор → раздел → пункт → подпункт, закон → статья → часть → абзац → примечание. Единица поиска — структурная единица (пункт, часть, абзац), а не окно фиксированной длины: так ссылка в ответе всегда указывает на конкретный пункт. Единицы длиннее 1500 знаков режутся на окна ~1100 знаков по границам строк. К тексту каждого фрагмента приклеивается контекстный заголовок: название документа, предмет договора, срок действия редакции, раздел, номер пункта, пометки об изменениях («изменён доп. соглашением № …»). Демо-база: 21 документ → 364 единицы → 452 фрагмента (медиана 590 знаков, 90 % короче 1200).

**Иерархия поиска** (сверху вниз, каждый уровень сужает предыдущий):

| Уровень | Что делает | Выход |
|---|---|---|
| 0. Реестр | номер договора / статьи / пункта из разбора → точный фрагмент закрепляется сверху | пины |
| 1. BM25 | по леммам (pymorphy3), отдельно по каждому запросу: исходный вопрос, переформулировка, подвопросы, синонимы | top-40 на запрос |
| 2. Векторы | bge-m3 по тем же запросам, косинус по матрице фрагментов | top-40 на запрос |
| 3. Слияние | RRF с весами каналов, приоры (преамбула, реквизиты, подписи понижены), усиление документов, названных в разборе | top-60 |
| 4. Реранкер | bge-reranker-v2-m3 локально / Qwen3-Reranker-8B на платформе; оценка пары «вопрос — фрагмент» | top-24 |
| 5. Граф связей | к найденным пунктам добавляются изменяющие доп. соглашения, письма-дополнения, другие редакции того же пункта, перекрёстные ссылки | до 14 фрагментов |
| 6. Оценка (LLM) | релевантность каждого фрагмента 0–3 | |
| 7. Отбор (код) | редакция на дату события и парная действующая, снятие утративших силу, покрытие всех договоров при неоднозначности | до 12 фрагментов в контекст |

Полнота: эталонный пункт попадает в контекст в 100 % вопросов стенда (72 из 72 с эталоном).

**Скорость поиска** (M1 Pro, модели локально): BM25 — доли миллисекунды; эмбеддинги 6–8 запросов — 60–150 мс; реранкер 24 фрагментов — 0,9 с; расширение и отбор — миллисекунды. Поиск по исходному вопросу стартует одновременно с LLM-разбором (≈2 с) и успевает раньше него; после разбора добавляются его запросы, а реранкер досчитывает только новых кандидатов (обычно 3 из 24, ≈0,1–0,3 с). В диалоге предварительный поиск и реранкер используют все реплики пользователя вместе: эталонный пункт стоит на тех же местах (1–2), что и при ранжировании по переформулировке из разбора, а реранкер после разбора не пересчитывается.

**Время ответа** (интерфейс, DeepSeek Flash через API, вопросы по одному; 32 вопроса: 18 демо организаторов и 14 синтетических разных типов, медиана):

| Этап | Секунды |
|---|---|
| Разбор вопроса (LLM) + поиск параллельно | 2,0 |
| Досчёт поиска после разбора | 0,3 |
| Оценка фрагментов (LLM) | 1,4 |
| Два первых согласных варианта с рассуждением + проверка и дополнение выбранного (LLM, параллельно) | 3,2 |
| **Итого** | **6,9** (p90 8,4, максимум 9,0) |

Почти всё время — четыре последовательных обращения к языковой модели. Каждое стоит около 1 с независимо от длины запроса (12 и 12 000 входных токенов отвечают одинаково) и ещё около 4 мс на каждый токен ответа; локальные вычисления занимают около 0,3 с. Соединения с API держатся открытыми 90 с, поэтому вопрос после паузы не тратит время на установку соединения. Хвост дают многочастные вопросы с длинным ответом.

### Контроль достоверности

| Ситуация | Механизм |
|---|---|
| Недостаток информации | статус `partial` или `insufficient`, перечень недостающего |
| Ошибка в вопросе | разбор выделяет утверждения пользователя, генерация обязана их проверить (`false_premise`); несуществующие статьи и законы ловятся реестром |
| Дата и редакция | применимость каждой редакции к дате события вычисляет код и пишет во фрагмент («применяй» / «не применяй»); условия доп. соглашений идут в контекст; у законов даты изменений из пометок Гаранта, и если событие было до изменения, ассистент сообщает, что редакции на ту дату в базе нет |
| Отсылки за пределы базы | если норма отсылает к статьям того же закона, которых нет в базе, код помечает это во фрагменте, и ассистент называет недостающие статьи |
| Случайные ошибки модели | несколько вариантов ответа и голосование большинством по статусу и выводу |
| Ответ строго по вопросу | разбор не расширяет вопрос; доп. соглашения и утратившие силу редакции попадают в контекст только по словам пользователя или по дате события; дата, названная словами («завтра», «в этом году»), не подменяется календарной; в отказе на противоправную просьбу приводится только требование, которое просят обойти |
| Противоправные запросы | флаг на разборе, статус `refusal_illegal`, разъяснение требований по документам |
| Роль и давление | история передаётся только как реплики user/assistant, «системные сообщения» в тексте игнорируются, на «вы ошиблись» — повторная проверка по базе |
| Инструкции внутри документов | фразы, обращённые к ИИ, при индексации помечаются и исключаются из поиска |
| Выдуманные ссылки и числа | ссылки проставляет только код по маркерам; числа сверяются с фрагментами и вопросом с учётом сумм прописью, дат в обоих написаниях и расчётов (процент от суммы, сдвиг даты на срок); цитаты сверяются дословно; неподтверждённое отправляется на исправление |

## Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_API_KEY` | ключ API генеративной модели (обязательно; в репозиторий не попадает — `.env` в `.gitignore`) | — |
| `LLM_BASE_URL` | OpenAI-совместимый API генеративной модели | `https://api.deepseek.com` |
| `LLM_MODEL` | модель | `deepseek-flash` (на платформе — `deepseek/deepseek-v4.1-flash`) |
| `EMB_PROVIDER` | `api` (`/embeddings`), `local` (bge-m3 в контейнере), `off`, `auto` | `auto` |
| `EMB_MODEL` | модель эмбеддингов в API | `baai/bge-m3` |
| `RERANK_PROVIDER`, `RERANKER_MODEL` | реранкер `/rerank` | `auto`, `qwen/qwen3-reranker-8b` |
| `REASONING` | режим рассуждения модели: `auto` (проверка поддержки API), `on`, `off` | `auto` |
| `CANDIDATES` | число вариантов ответа, из которых выбирается согласованный (1 — без голосования) | `3` |
| `RERANK_TOP_N` | сколько кандидатов поиска проходит через реранкер | `24` |
| `VERIFY` | LLM-проверка выбранного варианта по фрагментам | `true` |
| `COMPLETE` | дополнение ответа сведениями из пунктов, на которые он ссылается | `true` |
| `PROFILE` | `accurate` (до 24 фрагментов на оценку доказательств) или `fast` (до 14) | `accurate` |
| `MAX_WORKERS`, `LLM_CONCURRENCY` | вопросов в обработке одновременно и одновременных запросов к модели (сабмит) | `6`, `12` |
| `TIME_BUDGET` | бюджет времени сабмита в секундах: после половины оставшиеся вопросы идут по быстрому пути (один вариант, без LLM-проверки) | `1200` |
| `PUBLIC_BASE_URL` | адрес, по которому пользователь открывает документы по ссылкам | `http://localhost:8000` |
| `WITH_LOCAL_MODELS` | собрать образ API с локальными bge-m3 и bge-reranker-v2-m3 (CPU) | `true` |
| `WEBUI_PORT`, `LEGAL_API_PORT` | порты | `3000`, `8000` |

Если API не предоставляет `/embeddings` и `/rerank` (например, DeepSeek напрямую), векторный поиск и реранкер работают на локальных bge-m3 и bge-reranker-v2-m3 внутри контейнера. Образ без них (`WITH_LOCAL_MODELS=false`) работает на лексическом поиске и LLM-оценке доказательств.

## Сабмит на платформу

```bash
python submission/build_zip.py        # → dist/submission.zip
```

Архив содержит `solution.py`, пакет `legal_core`, `requirements.txt` и заранее построенный индекс демо-базы. Платформа кладёт `data/questions.csv` и `data/kb.zip`, решение пишет `submission.csv` (`id,answer`). Если хэш базы не совпадает с заранее построенным индексом, индекс строится при запуске, а эмбеддинги считаются через API платформы. При сбоях эмбеддера, реранкера или LLM решение деградирует, но не падает: `submission.csv` записывается всегда.

## Стенд оценки

```bash
python eval/run.py --dataset eval/datasets/demo.jsonl eval/datasets/synthetic.jsonl --split dev --tag my-change
python eval/judge.py runs/<папка прогона> --model deepseek-flash --name judge_flash
python eval/leaderboard.py --judge judge_flash   # сводная таблица прогонов
python eval/retrieval_eval.py -v          # качество поиска без LLM
python -m pytest -q                       # регрессионные тесты парсера, рендера и API
```

Наборы: 18 демо-вопросов организаторов и 82 синтетических вопроса по всем ситуациям кейса (`split`: `dev` и `holdout`) с эталонными ответами и эталонными пунктами.

## Известные ограничения

- Законы в базе представлены отдельными статьями только в действующей редакции; для событий до даты изменения ассистент сообщает, что старой редакции нет.
- Определение номеров частей в статьях без нумерации (ТК РФ) основано на структуре абзацев выгрузки Гаранта.
- Качество векторного поиска на платформе зависит от доступности `/embeddings`; без него используется лексический поиск.
- Ответы модели не детерминированы: один и тот же код на 80 вопросах даёт оценку судьи с разбросом около ±0,01 между прогонами, поэтому варианты сравниваются по нескольким повторам.
- Три варианта ответа и их проверка увеличивают расход токенов примерно втрое; на время ответа это почти не влияет, потому что варианты генерируются и проверяются параллельно.
